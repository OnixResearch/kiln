# Recovery, qualification, and campaign blockers

This runbook covers journal/outbox recovery, the isolated maintained-cohort OnixOS pilot, readiness reconciliation and host qualification records, and selected campaign progress, controls, fan-out runbooks, and Cairn change tracking.

For the operator runbook index, see [the operator guide](../operator.md).

## Recovery

Restore the latest committed journal snapshot. Then classify each outbox lease.

Reconcile expired or ambiguous effects before redispatch. Do not claim exactly-once provider execution.


## Isolated maintained-cohort OnixOS pilot

`scripts/onixos-ci-pilot.py` runs one fresh, private operation through the
maintained Aspen host/extension, a real Lattice workflow, the explicit Onix
evaluator and `kiln-onixos-worker`. `kiln-onixos-pilot` authenticates the
operator request and persists existing core commands/events; HTTPS observation
is rebuilt from that canonical journal, not a constructed fixture state.
Kiln maintainers own the runner, source-binding contract and repeatability rail.
Operators own acquisition, worker isolation and the selected runtime cohort.

Provision the normal `kiln` package (which installs both pilot binaries), the
separately pinned `kiln-aspen-host`, its matching extension, the reviewed Lattice
producer and the optional Onix evaluator/plugin cohort before execution. Use a
frozen Kiln source tree, not a changing checkout, for retained qualification.
`nix develop path:$PWD` supplies Python and the normal Rust/Nickel tools; it does
not provision the external runtime cohort or grant remote mutation authority.

Supply an operator-owned Nickel input record admitted by
[`config/onixos-ci-pilot-inputs.ncl`](../../config/onixos-ci-pilot-inputs.ncl).
Every executable is an explicit absolute path. The consumer, WASM shim and
plugin are separate immutable NAR-pinned trees. `nixpkgs_url` must exactly match
the consumer's **root input edge** in `flake.lock`, not an arbitrarily named
`nodes.nixpkgs` entry. A different selected shim/plugin requires
`producer_substitution_reason`; the receipt retains the original locked
`onix-wasm` entry alongside that explicit substitution. Drift never selects a
fallback. The Radicle RID, exact published revision and actor describe genuine
operator ingress source facts; they do not pretend that the independently
selected OnixOS snapshot was published as that revision.

With `PILOT_SOURCE`, `PILOT_INPUTS`, `PILOT_NICKEL` and `PILOT_ROOT` naming the
frozen Kiln source, admitted input record, exact bootstrap Nickel executable and
a new private scratch prefix respectively, run each real case:

```console
for case in success build-failure evaluation-failure; do
  python3 "$PILOT_SOURCE/scripts/onixos-ci-pilot.py" \
    --inputs "$PILOT_INPUTS" --nickel "$PILOT_NICKEL" \
    --root "$PILOT_ROOT-$case" --case "$case" || break
done
```

Existing scratch roots are refused. Each run has finite process, output,
request, journal and recovery bounds, fresh signing/UCAN/TLS credentials and
private sockets/state. The Lattice worker's temporary directory is privately
bound through Bubblewrap to avoid sharing its pathname-based temporary state;
this is not a hostile-workload confinement claim.
The UTF-8 `root/eval-roots/<64-byte BLAKE3 hex>` path must fit Kiln's
128-byte provider-reference limit. Choose a short scratch prefix for every case;
unrepresentable root identities are rejected during profile admission, before
evaluator directories or processes are created.

Preparation discovers the real launcher, activation script and home-file
derivations generated by the consumer's inventory and Nickel `home-tools`
service. A fresh BLAKE3 build identity is bound into the inventory's `git_user`
setting, changing the real generated configuration and its transitive outputs.
Only external toolchain dependencies are realised during preparation; their
transitive derivation and output closures must exclude all three consumer
identities. Immediately before authenticated dispatch, every selected consumer
output must be absent both physically and from native Nix path metadata.
Authenticated CI then constructs the complete selected launcher closure through
the existing no-substitution, no-remote-builder Nix adapter. Success verifies
the generated Git configuration and exact activation/home-file closure members.
It does not execute activation, install profile wrappers or mutate a home.
`provisioning.json`, `before-dispatch.json` and `verification.json` retain this
boundary. An already realised consumer output is rejected, never deleted.

The build-failure case adds a typed file target beneath the real `.gitconfig`
file and requires the actual home-file builder's conflicting-target diagnostic.
A failed builder may leave an unregistered partial directory: evidence records
physical presence separately from native registration and never treats that
directory as a successful product. The fresh pre-dispatch check still rejects
any pre-existing physical consumer output.

The deterministic preparation-policy regressions can be repeated independently:

```console
nix build path:$PWD#checks.x86_64-linux.onixos-pilot-preparation --no-link -L
```

The success case must produce canonical `Success` and exact retained output
roots. The genuine failing derivation must produce `DomainFailure`; the
explicit evaluator control must retain its native diagnostic, produce
`ProviderError` and never create a build plan. Every case exercises tampered
and expired request denial, duplicate delivery before and after completion,
host restart while the independently owned workflow is still pending, and
reconciliation of the original operation with exactly one provider invocation.
Roots survive durable result/journal handoff, then explicit release is repeated
to establish idempotence. UCAN HTTPS probes verify actual run/attempt views and
their identities, and require wrong-holder, wrong-target and replay denial.
Derivation-root cleanup requires a nonempty handoff authorized by the existing
core decision. Failed or unknown discoveries keep their root observation;
they do not invent a downstream handoff. Qualification also rejects terminal
worker errors emitted after a durable result, and requires completed discovery
to discharge its authorized derivation-root release.

Retain `cohort.json`, admitted public profiles, the signed request's public
facts, native discovery/build results and diagnostics, canonical journal,
`verification.json` and `retirement.json`. Never retain private keys or
invocation/bearer credentials. The runner stops its processes and retires
private credential files on success or failure. A receipt is valid only for
its measured source/input/executable/profile cohort. It establishes neither
autonomous forge delivery, production state/status mutation, deployment,
source trust, general exactly-once execution, reproducibility nor release
eligibility. See the [license map](../../LICENSES.md) before distribution.

The [historical launcher-only qualification](../../.cairn/archive/1970-01-01-qualify-maintained-onixos-ci-pilot/evidence/verification.json)
binds the actual `Success`, `DomainFailure` and `ProviderError` cases to frozen
source, executable and input identities, with complete public command records
and an implementation-byte manifest. Its native repository readiness
conformance passes with `onix_release_ready = false`; this is not production
readiness or release approval.
The [full-closure qualification](../../.cairn/archive/1970-01-01-build-authenticated-onixos-home-closure/evidence/verification.json)
retains the new construction evidence separately. Its frozen runner/projection
identities and before/after consumer observations bound that stronger build
claim without extending deployment, publication or release authority. A second
success uses the same immutable source with a fresh, previously absent consumer
closure; it does not substitute cached consumer outputs for construction.

## Selected campaign progress and blockers

The selected-campaign projection is a separate versioned contract
(`kiln.selected-campaign-projection.v1`); it does not change resource inventory
v2. It reads only an existing canonical campaign snapshot and its stored
version. A campaign snapshot records admitted owner observations, not independent
provider truth. Stages, blockers, evidence, input freshness, current work/attempt
bindings, pending effects and remaining obligations are displayed as observations;
a proposed next action is not a reservation, dispatch, successor, landing or
lifecycle grant.

`next_action` comes with `selection_basis`, which records why that decision was
chosen: a campaign barrier, the first member action, a surfaced member hold
because no member can act, or no eligible member. Each member carries its
retained `selection_hold`, the wait, blocker or replan that keeps it from being
selected, with reason, owner and any review request identity. A member waiting
for review keeps its hold while an independent member is the next action. The
console shows the hold on each member row. Projections produced before this
field existed show "none recorded".

The payload exposes a stable digest of the repository binding rather than a raw
repository path. Campaign/member IDs are retained because they are the exact
selection identities; treat them as operator data.

The offline consumer accepts an explicit canonical database and exact
campaign selector:

```sh
kiln-web-service campaign-projection DATABASE CAMPAIGN_ID [json|html]
```


Live, CLI and offline consumers can use the same optional resource composition
helper with a principal-admitted inventory projection. The final identity hashes
the full bounded redacted semantic payload after canonical current-work and
optional resource joins, with its own identity field cleared during hashing.
If no resource projection is admitted, work/attempt/resource joins remain unknown;
the separate resource inventory continues to report its own unavailable state.
Offline HTML is inert and uses the same bounded semantic projection as CLI JSON;
it performs no discovery or network request. A missing campaign is reported as
missing, while a missing member observation remains visible with unknown stage.
Worker capability, execution capacity, model admission and aggregate-budget
exhaustion require their own current owner observations; absent evidence must not
be interpreted as a free slot or exhausted budget. Inventory source failures
remain independent and are not used to hide campaign data.

### Campaign controls and decision inbox

<!-- r[related kiln.implementation.campaign.controls] -->
Campaign controls are optional. Export a profile from
`config/web-campaign-controls.ncl` (positive and negative inputs are under
`config/fixtures/*web-campaign-controls-*.ncl`) and pass it to both `check` and
`serve`:

```text
kiln-web-service serve --profile SERVICE --implementation-work DATABASE --campaign-controls CONTROLS
```

The profile names the campaign database, which must be the same file as
`--implementation-work`, so the console controls exactly what it displays. It
grants exact principals (never wildcards) a set of campaigns, a subset of the
commands `start`, `continue`, `pause`, `cancel`, `issue_decision` and
`resolve_decision`, optional review roles and an optional `not_after_ms`
expiry. It also lists definitions: frozen `CampaignContract` JSON files, each
with its delivery route (`github_pull_request` or `native_git`). The service
rereads the profile for every control request, so removing a grant or letting
it expire takes effect on the next request without a restart. An unreadable or
invalid profile refuses every control with `campaign_controls_unavailable`.

| Route | Method | Purpose |
| --- | --- | --- |
| `/api/implementation/campaign-definitions` | GET | Start previews: exact members, tasks, prerequisite inclusion, workflow profile, policy, repository instructions, goals, required checks and reviews, parent budget, the goals the route offers, any existing campaign and why a start is refused |
| `/api/implementation/campaigns/inbox?campaign=ID` | GET | Admission state, store version, the caller's open operations and every decision with category, state, question, options, recommendation, bound scope, scope freshness and the caller's actions |
| `/api/implementation/campaigns/commands` | POST | One typed intent with a client `request_id`, bound to the displayed `expected_version` or, for `start`, a `definition_identity` |

Viewers read previews and the inbox but get no operations. Worker principals
are refused all three routes. Operators act only within their current grant;
answering a required review also needs one of the member's review roles. Every
403 joins the existing denial audit and never reaches the campaign owner.

The canonical owner applies each command and records it, with its actor and
outcome, in the campaign database in one transaction. Resubmitting the same
request ID with the same intent returns the recorded outcome with
`replayed: true`, including after a service restart; reusing a request ID for
another intent or principal is `campaign_request_conflict`. A stale version,
a changed definition, an answer whose member moved to another work, policy or
candidate, a closed admission or a full decision bound returns 409 and applies
nothing. A start only creates the exact previewed selection: a definition
whose identity changed since its preview, or that lists a goal its delivery
route does not offer, is refused, and an existing campaign is never joined.

Pause stops successor admission and decision issuance; continue reopens it;
cancel closes the campaign permanently. None of them stops running attempts or
workers, observes cleanup or refunds usage, and retained effects still
reconcile. Accepted answers and continued admission wake the campaign
continuation.

In the console, the Workers page's campaign card shows admission controls and
the decision inbox below the projection, and **Start a configured campaign**
lists previews. Only listed operations appear. Cancel needs an explicit
confirmation. Each submission carries the displayed store version and a fresh
request ID. After a lost response, **Retry the same request** resends that ID,
so the owner returns the recorded outcome instead of applying the command
twice. A 409 reports that nothing was applied and reloads the current state.

### Runbooks and parent fan-out runs

Reviewed runbooks are defined via `config/runbook-registry.ncl` and passed to
`kiln-web-service serve --runbooks PATH` (with optional `--runbooks-dir DIR`
to enforce fail-closed on-disk BLAKE3 verification of Lattice bundle manifests
and assets before preview or dispatch). The four reviewed seed runbooks
(`flake-update`, `security-audit`, `license-ci-scaffold`, and `release-cut`)
live in the separated `runbooks/` directory in a `lattice#29`-ready operation
pack (`runbooks/packs/kiln-seed-runbooks/`); see
[`runbooks/MOVE_PLAN.md`](../../runbooks/MOVE_PLAN.md) for the migration plan into
a dedicated Lattice catalog repository. Each runbook may declare an optional
`approval_gate` (`"none"` or `"kiln_publication"`; `read_only` runbooks must
use `"none"` and empty `write_scopes`) and an optional
`fanout` policy (`default_max_concurrency`, `max_concurrency_limit`,
`default_budget_cap`, `max_budget_cap`, `max_targets`, and `write_scopes`);
`read_only` runbooks must declare an empty `write_scopes` list.

Operators can preview effects, resolved target revisions, typed parameter
bindings, approval gates, bundle pin verification, fleet claim overlaps, and
budgets without mutating state via destination `1.5` (Runbooks),
`POST /api/runbooks/{id}/preview`, or `kiln-web-service ci preview` (or
`--dry-run` on `ci dispatch`/`ci fanout`). Operators can dispatch a parent
fan-out run from destination `1.5` (Runbooks),
`POST /api/runbooks/{id}/fanout`, or `kiln-web-service ci fanout`:

- **Enrolled-project target expansion**: explicit target lists (`REPO@REF` or
  project/repo selectors) and globs (`target_globs`) resolve strictly against
  enrolled projects intersected with `allowed_targets`. Unenrolled or unallowed
  targets are refused before admission, and exact commit revisions are frozen
  per child at expansion time.
- **Bounded concurrency and budget caps**: admission never exceeds
  `max_concurrency` active children and stops once the parent `budget_cap` is
  drawn, marking remaining pending children `skipped` with recorded reason
  `fanout_budget_exhausted`.
- **Partial-failure isolation**: one child's failure or `Unknown` outcome
  releases its concurrency slot without cancelling or blocking siblings and
  never triggers blind retry.
- **Admission-only controls**: `pause`, `continue`, and `cancel` require an
  explicit `request_id` (replayed -> `replayed: true`, conflict -> `409`),
  re-check runbook authorization and definition parity on `continue`, and stop
  or resume future child admission only without claiming to stop
  already-running child runs.
- **Fleet claim overlap**: when `--fleet` is configured, mutating fan-outs check
  `<owner>/<repo> <path>` scopes against live fleet claims (`refuse`, `skip`, or
  `serialize`) and serialize overlapping internal mutating runs.

### Runbook result roll-ups

Kiln retains read-only result roll-ups across standalone runbook dispatches and
parent fan-out runs (`GET /api/runbooks/dispatches`,
`GET /api/runbooks/dispatches/{run_id}/rollup`, and
`GET /api/runbooks/fanouts/{fanout_id}/rollup`, plus `kiln-web-service ci`
`dispatch-list`, `dispatch-rollup`, and `fanout-rollup`). Destination `1.5`
(Runbooks) renders roll-ups both from **Recent dispatches** / **Inspect result
roll-up** and inside the fan-out inspector (`#fanout-rollup-section`) with
bounded cursor pagination (`rollup_cursor`):

- **Explicit outcomes**: per-target exact `source_revision` and canonical run
  `Outcome` preserve `Outcome::Unknown` and `Skipped` explicitly and never
  collapse a parent fan-out into a single fabricated pass/fail outcome.
- **Explicit receipt states**: Patchgate review receipts
  (`kiln.patchgate.review.v1` `ReportKind::Review` uploads) and verification
  receipts (run-bound `Gate`, `Provenance`, `Junit`, `Cobertura`, `Lcov`
  reports, independent verification runs, and read-only `--implementation-work`
  records) explicitly show `present`, `missing`, `unrun`, or `unavailable`
  (`missing`/`unreadable`). Missing or unrun receipts are never treated as
  passing, and `grants_authority` is always `false`.
- **Validated PR and stack links**: observed pull request and stack URLs from
  `ImplementationObservation` (`PublicationRecord`) and run-bound report
  evidence are validated strictly as `https://` URLs with no embedded userinfo
  alongside their observed state (`open`, `closed`, `merged`, `draft`,
  `unknown`, `unobserved`) and claim no landing or CI acceptance.
- **Idempotent summary notifications**: `config/runbook-registry.ncl` may
  declare optional `notifications` webhook receivers (`kiln.runbook-summary-notification.v1`)
  delivered at most once per `(registration_id, subject_kind, subject_id)`
  completion (including `Unknown` when `on_unknown` is enabled). Reservations
  left `"reserved"` across a restart transition to `"ambiguous"` without
  retrying, and payloads omit `params`, `env_bindings`, `source_env`,
  credentials, and raw logs.

- **Fleet & Workers → Machines** browses windows only on hosts in the coordinator's attached Herdr inventory. A capture rechecks the selected pane on that host and returns bounded text to operators only. **Open viewer** asks the same operator-only route for `format=ansi&source=visible`: Kiln rechecks the pane, reads its Herdr layout size and visible screen (`pane read --source visible --format ansi`), and returns at most 64 KiB and 1000 lines. The console then loads the generated Rio viewer (`/herdr-viewer.js`, `/herdr-viewer.wasm.b64`; notices at `/herdr-viewer-notices.txt`) and paints the cells on a canvas. Escapes are interpreted only as terminal state; markup stays text, and clipboard, title, link, image and reply sequences are dropped. The viewer sends no input. It re-reads every 2 seconds while open and the page is visible, pauses while hidden, and stops when the pane leaves the host inventory or a read fails. If the module, WebAssembly or a 2D canvas is unavailable, the console shows the plain-text capture instead. The worst-case escaped JSON for a 64 KiB snapshot exceeds the smallest Web bridge `max_response_bytes` (65536); keep the documented 1 MiB profile so the viewer is not refused. Regenerate the assets with `nix develop path:.#dashboard-index -c python3 scripts/build-herdr-viewer.py`; the `herdr-viewer-assets` flake check runs it with `--check`.
- **Fleet & Workers → Attempts → Place independent work units** assigns 2–16 distinct, already-claimed, unstarted attempts to at least two explicitly selected hosts. Prepare unreserved units with `kiln-implementer claim` against the coordinator implementation database. The preview is not a reservation; an accepted reservation is not a running session. Read per-unit outcomes before acting on a lost response.
- **Fleet & Workers → Attempts → Move queued workload** changes the host on a current Herdr dispatch reservation only before a session is bound or any launch is recorded. A successful rebind is not a started agent. Running agent migration is unavailable; the provider does not supply a fenced checkpoint handoff and target resume.

### Cairn changes

<!-- r[related kiln.cairn.workspace] -->
The **Cairn changes** page (2.7) opens as a full-width register, with a List or
Board view over the same changes. Each change is keyed by its repository identity
(the BLAKE3 digest of the repository binding used by the campaign projection)
and its change name. One bounded read transaction over `--implementation-work`
joins exact canonical Cairn aliases (`cairn_task` or `cairn_artifact`,
`<change>/<unit>`), current and superseded work, attempts, verification,
publication and native lifecycle records, and selected campaign members. The
index and detail routes are **read-only**; neither grants claim, dispatch,
integration, lifecycle or campaign authority. Decisions can be answered or
issued here only through the separately admitted canonical campaign command
path described below.

| Route | Method | Purpose |
| --- | --- | --- |
| `/api/implementation/cairn` | GET | `kiln.cairn-workspace-index.v2`: changes with stage lane, unit spread, open decisions, first ranked blocker and counts |
| `/api/implementation/cairn/detail?repository=HEX&change=NAME` | GET | `kiln.cairn-workspace-detail.v4`: exact change's units, attempts, dependencies, memberships, decisions, ranked blockers, agent revisions and workflow revisions with a BLAKE3 view identity |

The console refuses older `v1` index and `v1` to `v3` detail documents rather
than inferring missing lane, agent or workflow facts. Viewers and operators may read both
routes; worker principals
are refused. The detail admits exactly `repository=HEX&change=NAME`: a
64-character lowercase hex identity and a percent-encoded change name of at
most 256 bytes without `/` or control characters. Both responses are bounded
to 4 MiB; the index lists at most 512 changes and reports truncation. Without
`--implementation-work` both routes return 503
`cairn_workspace_input_not_configured`, not an empty workspace. Only the
detail reads `--inventory`; see **Agents and revisions** below.

Each unit reads in five separate facets:

| Facet | Values |
| --- | --- |
| Readiness | `ready`, `blocked`, `unknown` (eligibility unavailable) or `not_admitted` (no current canonical work) |
| Execution | phase of the latest attempt on current work, or `not_started` |
| Evidence | `current_verified`, `current_failed`, `historical_only` or `none` |
| Integration | publication phase of that attempt, or `not_published` |
| Lifecycle | `receipt_observed` or `not_observed` |

The lane is a **summary position**, not readiness, acceptance, integration or
lifecycle authority. Its display order is **Needs attention** (`attention`),
**Awaiting work** (`awaiting`), **Ready to start** (`ready`), **In progress**
(`in_progress`), **Verified** (`verified`), **Integrated** (`integrated`) and
**Lifecycle recorded** (`recorded`). A blocked/unknown readiness, a stopped or
unrecognized current attempt, or failed current verification takes precedence
over any advance; without current work the unit awaits work. Otherwise the
furthest observed lane applies. A
change with any stopped unit needs attention, otherwise it uses the
least-advanced unit's lane (or awaits work when it names no unit). The unit
spread shows counts in every lane, while each unit retains all five facets.
Historical verification and unrecognized values never advance a unit.
Campaign-level review waits, holds, stale bindings and pending effects are
shown as blockers, not silently folded into the lane.

A unit comes from a canonical alias, a campaign task selection or a campaign
member's remaining obligations, and records which sources named it. A
whole-change selection names the change, not a unit. An attempt applies to
current work only when its work identity equals the unit's current canonical
version; otherwise it reads as historical. A lifecycle receipt counts only
when it binds the attempt's own work identity and fence; otherwise it reads as
crossed. A campaign member's binding is `current`, `stale` (superseded),
`unknown_work` (not in the ledger) or `not_bound`.

The register sorts independently of arrival: lane rank, blocker count
descending, open-decision count descending, change name, then repository
identity. List rows and Board cards show the lane, unit spread, first blocker
with subject and owner, open decisions, and attempt counts; each Board column
has a count. Search covers change, repository identity, projects and campaigns.
Choose one lane chip, toggle **Has blockers** or **Has open decisions**, or
clear filters; the count line shows matches out of the bounded total. Filtering
is local and immediate, with search committed to the URL after 350 ms rather
than issuing a read per keystroke. Arrow keys move among visible change links;
on the Board, left and right move between columns.

The URL binds `cairn_repository` and `cairn_change` together, plus
`cairn_unit` for one expanded unit. Register state uses `cairn_q` (at most 256
characters), `cairn_lane` (one known lane), `cairn_blocked=1`,
`cairn_decisions=1` and `cairn_view=board` (otherwise List). Reload restores
the selection, unit, filters and view. **All changes** clears the selection and
returns focus to its register link; **Previous** and **Next** use the filtered
order, or the complete order with an explanation if this change is outside the
filters. **Browse changes** reveals the preserved register in the detail. A
missing or malformed requested change or unit is named rather than replaced,
and a late response cannot draw over a newer selection.

The selected change fills the page. Its header gives the lane, unit spread,
projects and counts; **Next steps** ranks blockers by `dispatch_recovery`,
`dependency_cycle`, `no_acceptance_obligations`, `missing_dependency`,
`plan_not_accepted` (opt-in plan review only), `stale_work_binding`,
`pending_effect`, then `campaign_hold`, with subject and
observation breaking ties. Each blocker names its condition and meaning, exact
unit or campaign member, proposed operation, owner, display-only detail and
supporting observation (`work:`, `attempt:`, `campaign:ID@VERSION` or
`effect:`). Unit subjects open their unit; member subjects reveal the member
card and link its campaign. Reason text is never parsed into a decision. No
structured blocker on its own does not prove readiness.

**Units** is a five-facet matrix. Open one unit at a time to see its current
work title, outcome, revision, priority, terminal policy, acceptance
obligations, exact dependencies and current dependents, superseded versions,
and oldest-to-newest attempt timeline. The timeline distinguishes current
from historical attempts and shows phase, times, dispatch and unknown outcome,
verification with an exact run link, publication and lifecycle receipts.
Dependencies that are not current stay visible with their identity. The
**Dependencies** graph layers prerequisite to dependent, includes external
and not-current work, and marks cycles rather than looping. **Campaigns**
shows every selected member, including completion-only and waiting members:
binding, stage, selection and goal, admission, enumeration, hold and owner,
pending effects, remaining obligations and member blockers. **About this
view** keeps copyable repository and view identities, snapshot/truncation facts,
non-claims and the lane/facet legend outside the main reading path.

**Agents and revisions** (Lattice #24 and #25) reads the configured
`--inventory` input through the same principal-checked projection as
`/api/inventory`, never producer documents. The detail's `agents` section has
its own `source`: `admitted`, `not_configured` (no `--inventory`) or
`unavailable` with the refusal code, such as `inventory_principal_denied` or
`clock_unavailable`. A missing or refused inventory leaves the Cairn facts
readable and never reads as an empty fleet. The view identity binds the
inventory projection it was computed from.

Every revision fact is a slot with one of five states, each with its own
words on the page:

| State | Meaning |
| --- | --- |
| `recorded` | The producer recorded the value shown. |
| `not_recorded` | A managed lifecycle records no value for the projected revision, such as a revoked qualification. |
| `unknown` | The producer manages the fact but does not know it; `owner` names who can resolve it (`kiln#49` preparation, `animus#18` qualification, `lattice#25` selection and pins). |
| `unmanaged` | No producer revision lifecycle governs the definition or session. It is neither unknown nor unqualified. |
| `unpublished` | No producer publishes the fact. |

**Workflow revisions** come first and stay separate from worker revisions.
They come from the inventory's `workflow_revisions` sources, which Kiln
collects from Lattice's `lattice.workflow-agent-revision-slots.v1` documents
(see [inventory producers](../inventory-producers.md#workflow-revision-slots)).
They have their own `source`: `admitted`; `not_configured` when the inventory
profile names no workflow revision source; or `unavailable` with the source's
refusal code, such as `lattice_workflow_slots_unsupported_schema` or
`workflow_revisions_source_missing`. Neither hides the agent and worker
revisions. Each **workflow definition** shows its desired, last usable and
selected-for-new-sessions workflow revision as `recorded`, `not_recorded` or
`unknown`; a recorded selection's rollout generation, kind (promotion or
rollback) and qualification reference; and its pinned sessions, counted per
revision with status, **Pin blocked** and whether they are pinned to the
selected revision. Each workflow revision names the worker revision it pairs
with and whether that is the revision the inventory projects for the worker
definition, another revision, or a definition the inventory does not hold. Its
identities disclosure lists the compiler, compiler artifact, plan, graph,
Cairn selection, obligations and policy identities and the worker definition,
revision and bundle. Session identities, names and guidance, context or
source identities are never shown. Each **agent
definition** shows its observation state, profile revision, lifecycle
management, the desired, prepared, qualified and selected-for-new-sessions
slots, the rollout generation of a recorded selection, declared task families,
tools, harnesses, output contracts and models (`declared`, `none` or
`unknown`), authority, and its wait reasons as `code · subject · owner`. A task
family shows its qualification reference, evidence class and provenance. Only
`live` provenance reads as live evidence; a `fixture` reference reads
**Fixture evidence, not live**. Each **worker** shows its lifecycle, pinned
revision, whether that matches the definition's selection (`matches_selected`,
`differs_from_selected`, `no_selection` or `definition_not_observed`), its pin
(status, qualification reference, rollout generation and pin identity, or the
pin's slot state), **Pin blocked** when further effects are refused, and its
wait reasons. A worker whose attempt and fence equal an attempt of this change
reads **On this change**, lists first and shows that attempt. Other workers
read **Other work** or **No attempt** without the identity.

The section never copies sessions, workspaces, execution allocations or
grants, model-service bindings, full qualification records, preparation
failures or other work's attempts, even when the inventory profile includes
evidence. Until capability-scoped observers exist (#69/#70/#75/#76/#79), every
viewer and operator admitted to the inventory sees the same section. Kiln does
not yet bind a Cairn unit to the definition its work needs (#83), so the
section lists every definition and worker in the inventory.

Open decisions follow the blockers. For each campaign, the page reads its
inbox and matches exact decision identity and this change's member key. Only
the inbox-listed **Submit answer** (`resolve_decision`) or **Issue to
reviewers** (`issue_decision`) action is mounted for the principal; if controls
or inbox are unavailable, or no action is listed, the decision remains
read-only with a campaign link. These commands go to
`/api/implementation/campaigns/commands`, not to either Cairn GET route. The
shared campaign runner submits the inbox store version and a fresh request ID;
a retry after an uncertain response reuses that ID, and a 409 reports nothing
applied and reloads. Applied commands reload the change. Start, pause,
continue and cancel are available only through the campaign's own controls,
never here. This does not imply any worker, remote provider or lifecycle
completion occurred.

For repeatable rehearsal, start the disposable explorer above and open its
**Cairn changes** examples: A has a failed prerequisite attempt and needs
attention; B depends on A's exact current work and is ready despite a campaign
review wait; C has a historical superseded attempt, a stale campaign binding
and current in-progress work; D is completion-only, with no canonical work and
an awaiting-work lane. Try List/Board and URL filters, then a change's next
steps, unit expansion/timeline, A→B graph, campaign link and an inbox-admitted
decision action if offered. These are local synthetic canonical stores, not a
live campaign or provider execution. Requirement text is limited to canonical
acceptance obligations; native Cairn requirement references are not read.

Canonical work keys hash the alias set without the repository. Two enrolled
repositories naming the same Cairn unit therefore collide in the work ledger,
and the page cannot show work the ledger refused or replaced.
