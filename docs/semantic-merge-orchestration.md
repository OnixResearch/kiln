# Semantic merge check orchestration

Kiln can check an already proposed merge M against an exact base O and variants A and B. The check is opt-in. Kiln binds an externally produced semantic checker result to that frozen quartet and to an explicit policy, then interprets the result as a CI decision.

Kiln does not:
- generate or mutate M;
- infer a merge base;
- implement merge semantics;
- grant merge, publish, status or release authority.

[Verified Three-Way Program Merge](https://www.microsoft.com/en-us/research/wp-content/uploads/2018/11/verified-merge-oopsla-18.pdf) motivates the check. Language-owned tools perform it.

Status: this is a design contract with a pure core (`kiln_core::semantic_merge`), a producer port (`kiln_provider_api::semantic_merge::SemanticCheckerPort`) and fixture proof. A required production gate waits for three things:
- the Rust producer ([Octet #1](https://github.com/OnixResearch/octet/issues/1)) or the Noble checker ([Noble #30](https://github.com/OnixResearch/noble-lang/issues/30));
- typed result and applicability bindings ([Valence #1](https://github.com/OnixResearch/valence/issues/1));
- independently reviewed checker support.

Only the fixture producer in `crates/kiln-adapter-pijul/tests/semantic_merge.rs` implements the port today.

## Evaluation request

`SemanticMergeRequest` is admitted once by `admit_request` into an immutable `AdmittedRequest`. It carries:

| Field | Content |
| --- | --- |
| `base`, `variant_a`, `variant_b`, `candidate` | One `RoleSource` each: the role tag, the exact `SourceResolution` (provider profile, repository, symbolic reference, exact revision, canonical tree, native facts) and the source profile it was acquired through. |
| `candidate_supply` | The supplier profile, the native proposal reference, and the state the supplier proposed. |
| `subject` | Language, semantic unit, and the sorted set of required coverage units. |
| `property` | Property id and revision, plus sorted assumption identities. |
| `inputs` | Dependency closure identity and semantic model identity. |
| `checker` | Producer profile, checker binary, toolchain, semantic profile and receipt profile. |
| `policy` | Mode, lineage policy, admitted checkers, source profiles and candidate suppliers, retry policy and bound ceilings. |
| `bounds` | Wall time, memory, stdout and stderr bytes, and product count. |

Admission rejects the following before any effect, with a diagnostic naming the field:
- a role in the wrong slot, or a mixed source provider;
- an unadmitted profile, checker or supplier;
- unsorted or unbounded sets;
- zero bounds, or bounds above the policy ceiling;
- unavailable or ambiguous lineage.

## Bindings

Admission computes a `RequestBinding`: one BLAKE3 identity per component, plus an overall identity over all of them. The components are:
- `base`, `variant_a`, `variant_b`, `candidate`;
- `candidate_supply`, `subject`, `property`, `assumptions`;
- `dependencies`, `model`, `checker`, `policy`, `bounds`.

Each role component hashes its role tag with its source identities. Equal trees in different roles, or exchanged A and B, therefore never collide.

Derived identities:
- **Attempt:** `attempt_binding(request, ordinal)`.
- **Log or product:** `artifact_binding(request, attempt, kind, name, content)`.
- **Cache key:** the overall request identity.

Every rejection names the failed binding, for example `semantic_binding_mismatch` at `semantic_merge.binding.dependencies`.

## Lineage and Pijul provenance

Selection is explicit. `LineagePolicy::DeclaredRoles` accepts the operator's roles and checks no ancestry.

`LineagePolicy::PijulChangeContainment` requires Pijul native facts for every role. It treats each channel state as its admitted change set:

- O ⊆ A and O ⊆ B (`semantic_lineage_base`);
- if `require_greatest_common_base` is set, O = A ∩ B. Variants that share a change outside O make the base ambiguous (`semantic_lineage_ambiguous`);
- A ∪ B ⊆ M (`semantic_lineage_candidate`), with at most `max_candidate_extra_changes` further changes (`semantic_lineage_candidate_extra`);
- a role without Pijul facts fails as `semantic_lineage_unavailable`.

Pijul provenance and content identity are distinct facts:

- **Provenance:**
  - the exact revision is the Pijul Merkle channel state;
  - the observation binds the repository, channel, ordered change sequence, before/after state and format cohort;
  - one change hash never stands for a state (`pijul_resolution_facts`).
- **Content:**
  - `canonical_tree` is Kiln's BLAKE3 identity over admitted bytes;
  - equal trees prove only equal bytes, not equal history, so the role binding carries both.

Kiln never computes a Git-style merge base. A Git ancestry policy is unsupported scope, and no such policy variant exists.

## Candidate acquisition

M is never generated by Kiln. A policy-admitted supplier names a proposal and an exact state. Kiln freezes that state through the same read-only source acquisition used for O, A and B:
- The acquisition profile must be the role's source provider and appear in the policy.
- It must use immutable resolution.
- It must hold only discover, resolve-exact, acquire and observe-identity.

Any mutate, collaborate, trigger, status or credential capability fails with `semantic_acquisition_authority`. A supplied state that differs from M fails with `semantic_candidate_supplied_state`.

The Pijul adapter gained no operation. `PijulRepositoryPort` still has only `discover_channels` and `resolve_and_acquire`. `pinned_profile_refuses_every_forbidden_source_capability` demonstrates three refusals:
- each forbidden `SourceCapability` is refused by the admitted profile;
- adding one to the profile fails admission;
- setting any of `allow_network`, `allow_credentials`, `allow_collaboration`, `allow_triggers`, `allow_status_publication` or `allow_mutation` fails admission before any repository read.

If candidate generation is ever needed, it must be a separately scoped and authorized service.

## State transitions

The core follows `state + command -> events + effects` (`decide`) and `state + event -> state` (`evolve`).

| State | Command | Events | Effects | Rejections |
| --- | --- | --- | --- | --- |
| new | `Dispatch` | `AttemptStarted(1)` | `DispatchChecker` | `semantic_dispatch_duplicate` after any attempt |
| new | `UseCache(entry)` | `CacheReused` | none | `semantic_cache_mismatch` (names the binding), `semantic_cache_nondeterministic` |
| attempt pending | `ObserveResult` | `ResultRecorded` | none | `semantic_attempt_replay` (unknown attempt), `semantic_result_late`, `semantic_binding_mismatch`, `semantic_binding_identity`, `semantic_checker_substitution`, `semantic_evidence_substitution`, `semantic_artifact_binding`, `semantic_product_bound`, `semantic_coverage_scope`, `semantic_coverage_missing`, `semantic_receipt_missing` |
| attempt pending | `ObserveFailure` | `ResultRecorded` (timeout → exhausted, cancelled, tool-error) | none | as above for the attempt |
| outcome recorded | `Retry` | `AttemptStarted(n+1)` | `DispatchChecker` | `semantic_retry_refused` |
| any, not terminal | `Cancel` | `EvaluationCancelled` | `CancelChecker` for the pending attempt | `semantic_evaluation_terminal` |
| any | `ObserveInputs(fresh)` | `InputsChanged(component)` when any component differs | `CancelChecker` for the pending attempt | none |
| stale | any result | none | none | `semantic_result_stale`; other commands fail with `semantic_evaluation_stale` |
| cancelled | any result | none | none | `semantic_result_late` |

Partial output from the right attempt records `ToolError` with `semantic_partial_output`; it is not rejected and not verified.

Retry rules (`classify_retry`):
- `ToolError` retries only if `retry_tool_error` is set and attempts remain under `max_attempts`.
- `Exhausted` retries only if `retry_exhausted` is set.
- Every other outcome is terminal.
- Each retry gets a new attempt identity. Results for earlier attempts become late.

`cache_entry` exports only `Verified`, `Counterexample` and `Unsupported`, the deterministic outcomes, for an unchanged, uncancelled evaluation.

## Modes and outcomes

The outcome lattice is: `Verified`, `Counterexample`, `Unknown`, `Unsupported`, `Exhausted(bound)`, `Cancelled`, `Stale(component)` and `ToolError`.

`decide_gate(state, fresh)` compares the recorded result with a fresh re-observation of every component (`reobserve_binding`).

| Mode | Satisfies | Blocks |
| --- | --- | --- |
| Required | only a fresh `Verified` result that matches the exact binding, comes from the admitted checker and covers every required unit | every other outcome, including none yet |
| Advisory | never | never |

`conflict_demonstrated` is true only for `Counterexample`. `Unknown` is neither success nor a demonstrated conflict.

## Independence and downstream revalidation

`combine_gates` requires every independently requested gate (build, tests, lints, review) and, separately, the required semantic gate. A verified semantic result does not satisfy a failing build. Passing build, tests, lints and review do not satisfy a non-verified semantic result.

None of these can substitute for a semantic checker receipt, and each is refused as `semantic_evidence_substitution`:
- a clean text or Pijul merge;
- equal source trees;
- passing tests;
- an accepted evidence envelope.

Every verdict carries a `RevalidationObligation`: the request identity and the exact state and tree of M, O, A and B. A downstream merge or publish shell must call `check_revalidation` inside its own race-safe protocol and fail on `semantic_revalidation_moved`. `grants_mutation_authority()` is always false. This contract adds no mutation authority.

## Integration plan with existing ports

1. **Source:** acquire each role with the existing source port. For Pijul, use `kiln_adapter_pijul::resolve_and_acquire` with the admitted `pijul-source-v1` profile. Re-acquire all four roles to build the fresh binding before deciding the gate.
2. **Dispatch:** `checker_workflow_plan` maps each attempt to a Lattice `WorkflowEffectPlan`:
   - one `Test` node of kind `semantic-merge-check`;
   - `adapter_kind` set to the checker semantic profile;
   - `operation_identity` set to the request identity;
   - `idempotency_key` set to the attempt identity;
   - cancel control enabled.

   The plan passes `validate_workflow_plan`. The single-revision `source` context stays unset, because the quartet travels in `operation_identity` and the checker request. No new Lattice interface is needed.
3. **Bounded execution:** the producer shell maps `CheckBounds` to Bounded Exec `ExecutionLimits`:
   - `timeout_ms` to `timeout_ms`;
   - `stdout_max_bytes` and `stderr_max_bytes` to the stream limits.

   Memory stays with the execution provider's resource limit. Mantle realizes any build the checker needs.
4. **Producer:** a language-owned shell implements `SemanticCheckerPort`. `dispatch_semantic_check` refuses a producer whose identity differs from the admitted checker before calling it. `producer_failure` maps port timeouts, cancellations and other failures onto recorded outcomes.
5. **Evidence:** Valence (#1) validates receipt identity and linkage. Kiln records the receipt identity and the artifacts bound to the request and attempt.
6. **Gate:** the shell persists events, publishes no status of its own, and combines the semantic verdict with independent gates.

## Fixtures

The human-authored fixture is `fixtures/semantic-merge/quartet-data.ncl`, typed by `contract.ncl` and applied by `quartet.ncl`. `quartet.json` is its deterministic `nickel export --format json` output. The `semantic-merge-fixtures` flake check runs these steps:
1. checks formatting;
2. re-exports the fixture and compares it byte for byte;
3. requires every `negative-*.ncl` contract fixture to fail.

The end-to-end test resolves the four channel states through the adapter mapping, then runs the request, the fixture producer, result admission and the CI decision. It also runs every negative case in the fixture:
- swapped roles;
- changed base, candidate, dependencies and policy;
- missing coverage;
- each non-verified outcome;
- partial output;
- a replay from another attempt;
- cancellation;
- a concurrent source change;
- each substitute evidence kind.

## Non-claims

`SEMANTIC_MERGE_NON_CLAIMS` is normative. CI success with a semantic merge gate does not prove or grant:

- any semantic guarantee outside the checked property for the exact role-tagged quartet, assumptions, dependencies, model, checker and policy;
- source trust, signatures or complete history;
- merge, publish, status or source mutation authority, including automatic merge;
- blanket release eligibility.

An unknown, unsupported, exhausted, cancelled, stale or tool-error outcome is neither success nor a demonstrated conflict. The fixture producer proves the orchestration only. It does not prove checker soundness, a receipt profile, or a production gate.
