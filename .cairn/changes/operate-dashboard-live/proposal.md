# Operate the dashboard over fresh CI history

## Why

The dashboard is interactive and has real retained history, but it has no continuously supervised path from newly written canonical CI journals to the Aspen3 report. Kiln operators need fresh observations without giving the dashboard execution or status authority.

## What Changes

- Read bounded candidate-local Radicle CI journals into a deterministic repository/history catalog, retaining exact source identities and unresolved outcomes.
- Invoke the existing real renderer and atomic publisher from one finite read-only collection cycle; failures retain last-good HTML.
- Package the collector and publisher together and provide a supervised producer-local user service/timer delivering only HTML to Aspen3.
- Exercise fresh real Kiln fork self-CI success and genuine build failure, then observe publisher restart/recovery and keep candidate-bound evidence.

## Impact

- Current consumer: the operator viewing `/home/brittonr/.local/share/kiln/dashboard/index.html` on Aspen3.
- Owner: Kiln dashboard maintainers own collection and publication; operators own source/controller state, SSH enrollment and supervision.
- Adoption: typed Nickel configuration, immutable installed executables, explicit state root, systemd user timer.
- Reuse: existing canonical journal admission, dashboard catalog/rendering, bounded publisher and dedicated native Radicle self-CI rail. The retired GitHub credential stack is not silently re-enabled.

## Authority

The user's instruction to begin the proposed closeout/live-operation work authorizes dashboard spec acceptance/archive, source publication, this narrowly named publisher service and dedicated fresh CI canary effects. Canonical Radicle governance, unrelated services, broad persistent forge credentials, activation and release remain out of scope.
